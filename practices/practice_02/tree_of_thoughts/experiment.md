# Tree of Thoughts

- Решение, для которого нужны альтернативы: выбрать способ заполнения пустого `practices/practice_01/analysis.md`, чтобы одновременно показать фактический AS IS, целевой TO BE, границы доверия и проверяемую разницу без выдумывания архитектуры.
- Критерии выбора: (1) подтверждаемость по `TRAINING_PR.diff` и `CASE.md`; (2) видимость потока данных и границ внешнего LLM; (3) рендеринг в GitHub без дополнительных файлов; (4) понятность для независимого ревью; (5) минимум неподтверждённых сущностей.

## Запрос

```text
Ты — системный аналитик. Нужно выбрать формат и заполнить только practices/practice_01/analysis.md для учебного сервиса AI-помощника ревьюера PR.

Источники фактов:
- practices/practice_01/TRAINING_PR.diff — фактический AS IS;
- practices/practice_01/CASE.md — обязательные SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1;
- practices/practice_01/context.md — допущения и неизвестные;
- текущий practices/practice_01/analysis.md — единственный файл для изменения.

Сначала внешне опиши три альтернативы: BPMN-подобный процесс, DFD-подобный поток данных в Mermaid и IDEF0-подобную функциональную декомпозицию. Для каждой перечисли плюсы, минусы и оценку по пяти критериям: evidence, границы данных, рендеринг GitHub, понятность, риск выдумать компоненты. Не показывай скрытую цепочку рассуждений.

Затем выбери одну альтернативу и непосредственно заполни analysis.md:
1. AS IS должен следовать только TRAINING_PR.diff: POST /api/reviews передаёт payload["diff"] в ReviewService; сервис включает diff в prompt, вызывает llm.generate и возвращает {"comment": answer}.
2. TO BE должен показать требования CASE.md как целевое поведение, не утверждая, что оно реализовано.
3. Сохрани разделы AS IS, TO BE, Разница и Как использовали AI.
4. Добавь Mermaid-диаграммы, которые рендерятся в GitHub.
5. В таблице Разница для каждого изменения укажи воспроизводимую проверку.
6. Явно перечисли неизвестные: контракт контролируемого ответа REL-1, точка логирования OBS-1, алгоритм удаления секретов, формат ответа внешнего LLM.
7. Не добавляй очереди, БД, gateway, UI, GitHub-клиент, роли согласования и другие неподтверждённые компоненты.

Перед завершением проверь, что изменён только analysis.md, все элементы AS IS видны в diff, все элементы TO BE связаны с правилом CASE.md, а неизвестные не названы реализованными.
```

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. BPMN-подобный процесс | Хорошо показывает событие, человека, систему и развилки | Для полноценного BPMN нужны пулы, события и роли, которых источники почти не описывают | Evidence 4/5; границы данных 3/5; GitHub 4/5; понятность 4/5; риск домыслов средний |
| B. DFD-подобный поток в Mermaid | Ясно показывает движение diff, внешнюю границу LLM, преобразования и ответы; использует подтверждённые узлы | Не моделирует календарные задержки и ответственность столь подробно, как BPMN | Evidence 5/5; границы данных 5/5; GitHub 5/5; понятность 5/5; риск домыслов низкий |
| C. IDEF0-подобная декомпозиция | Удобно разделяет входы, управления, механизмы и выходы | Труднее читать без нотации; механизмы и исполнители в источниках не определены | Evidence 3/5; границы данных 4/5; GitHub 3/5; понятность 3/5; риск домыслов высокий |

## Выбор

- Выбранная альтернатива: B — DFD-подобный поток данных в Mermaid.
- Почему: она лучше всего показывает критическую для кейса границу передачи diff внешнему LLM, позволяет рядом сопоставить AS IS и TO BE и не требует вводить неподтверждённые роли или инфраструктуру.
- Как проверим: каждый узел AS IS сопоставим со строкой `TRAINING_PR.diff`, каждый целевой контроль — с идентификатором в `CASE.md`; Mermaid-блоки проходят структурную проверку и визуальный просмотр в GitHub.

- Что отклонили: BPMN с неподтверждёнными ролями и IDEF0 с выдуманными механизмами; также не добавляли очереди, БД, gateway, UI и GitHub-клиент.
