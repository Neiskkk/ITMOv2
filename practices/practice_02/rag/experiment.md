## Запрос

Цель: изменить только `practices/practice_01/tests_integration.md`, чтобы интеграционные проверки соответствовали подтверждённым требованиям и реальным границам компонентов. Не выдавай требуемое CASE.md поведение за уже реализованное, если TRAINING_PR.diff его не показывает.

Порядок работы:

## Ответ со ссылками на источники

Текущий код подтверждает цепочку `POST /api/reviews -> review_service.review -> llm.generate`: API передаёт `payload["diff"]`, а сервис без показанной предварительной обработки включает diff в prompt и возвращает поле `comment` ([`TRAINING_PR.diff`, `app/api.py` и `app/review_service.py`](../../practice_01/TRAINING_PR.diff)). Поэтому существующие строки про маскирование, ограничение размера и соответствие OUT-1 следует оформить как проверки требуемого поведения и выявляемых разрывов, а не как описание уже реализованных функций.

Набор интеграционных сценариев должен покрыть удаление трёх типов секретов, границу длины diff, timeout внешнего LLM, выходной контракт, проверяемость рисков, безопасные логи и отсутствие действий в GitHub ([`CASE.md`: SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1, SCOPE-1](../../practice_01/CASE.md)). При этом точное место маскирования, внешний контракт схемы ответа, таймауты и ретраи вне показанного diff остаются неизвестными ([`context.md`, раздел `Что пока неизвестно`](../../practice_01/context.md)). Отдельный компонент `Нормализация`, middleware, gateway или GitHub-клиент источниками не подтверждены и не должны добавляться как факты.

## Что изменили в исходном артефакте

- Файл и раздел: `practices/practice_01/tests_integration.md`, таблица `Integration-проверки` и раздел `Как использовали AI`.
- Изменение: таблица расширена до двенадцати сценариев для фактической цепочки API -> ReviewService -> LLM и требований API-1, SEC-1, REL-1, OUT-1, QA-1, OBS-1 и SCOPE-1. Текущий `{"comment": answer}` зафиксирован как разрыв, а не как соответствие OUT-1.
- Как проверили ссылки: вручную сопоставили фактические связи API, ReviewService и LLM с `TRAINING_PR.diff`; ожидаемое поведение — с идентификаторами правил в `CASE.md`; допущения и неизвестные — с соответствующим разделом `context.md`.
- Что отклонили как неподтверждённое: существование отдельного компонента или функции нормализации, middleware, gateway и GitHub-клиента; конкретный код и схема контролируемого ответа; наличие ретраев; утверждения о реализации требований и успешном прохождении тестов без evidence или реального запуска.
