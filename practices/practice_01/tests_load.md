## Параметры запуска

- ENDPOINT: путь API приёмника diff - POST /api/reviews (из context.md). Хост/порт - Неизвестно.
- RPS: целевая интенсивность запросов по шагам. Значения — Неизвестно.
- STEP_DURATION: длительность одного шага нагрузки. Значение — Неизвестно.
- CLIENTS: число параллельных клиентов/воркеров. Значение — Неизвестно.
- CLIENT_TIMEOUT: таймаут клиента на ожидание ответа сервиса. Значение — Неизвестно.
- DIFF_SIZE: размер передаваемого diff для сценария; для границ используются ровно 19999; 20000; 20001 символ.
- DIFF_POOL: набор типовых diff <= 20000 символов. Источник/генерация - Неизвестно.
- SECRETS_SAMPLE: тестовые токены/пароли/ключи, используемые в diff. Формат и значения - Неизвестно.
- LLM_FAULT_MODE: режим имитации внешнего LLM (normal|timeout|unavailable). Способ включения - Неизвестно.
- LOG_SOURCE: источник логов сервиса для анализа (файл/stdout/агрегатор). Путь/доступ - Неизвестно.
- RUN_ID: идентификатор прогона для маркировки артефактов. Значение - на усмотрение запускающего.

## Порядок выполнения

1. Подготовка данных: сгенерировать и проверить длину тестовых diff (типовые <= 20000; ровно 19999; 20000; 20001). Подготовить варианты с тестовыми секретами.
2. Настроить параметры запуска: задать ENDPOINT, CLIENTS, CLIENT_TIMEOUT, STEP_DURATION, план шагов RPS, указать LOG_SOURCE. Зафиксировать конфигурацию как артефакт прогона.
3. Базовая проверка контрактов: по одному запросу каждого сценария вручную убедиться в соблюдении OUT-1, API-1, REL-1, SEC-1, OBS-1 (без нагрузки).
4. Нагрузочный прогон «Обычные diff»: запустить поток типовых diff с параметрами шага; собрать метрики и логи.
5. Нагрузочный прогон "Границы размера": отправить последовательности 19999, 20000 и 20001; проверить ожидания по API-1 и OUT-1.
6. Прогон "Медленный/недоступный LLM": включить LLM_FAULT_MODE, прогнать нагрузку и проверить соблюдение REL-1.
7. Прогон "Секреты": отправить нагрузку с тестовыми секретами; проверить, что исходящий prompt очищен (SEC-1).
8. Прогон "Логи": при устойчивой нагрузке собрать и проверить логи на соответствие OBS-1.
9. Ступенчатый исследовательский прогон: увеличивать RPS по шагам до появления признаков насыщения/деградации или срабатывания условий остановки. Фиксировать метрики на каждом шаге.
10. Сохранение результатов: собрать артефакты — конфигурацию, сырой трейс/метрики, логи, фикстуры diff, образцы исходящих payload LLM (для SEC-1/REL-1), сводную таблицу.

## Условие остановки

- Обнаружена утечка секретов в исходящем запросе к внешнему LLM (нарушение SEC-1).
- В логах появляется содержимое diff или ответ модели (нарушение OBS-1).
- Для diff <= 20000 начинает возвращаться HTTP 413 либо ответ перестает соответствовать OUT-1 (нарушение API-1/OUT-1).
- Внешний вызов не прерывается по таймауту 10 секунд и вызывает зависания/эскалацию ошибок вместо контролируемого ответа (нарушение REL-1).
- Устойчивое возникновение необработанных ошибок сервиса (например, серия 5xx) или массовые срабатывания CLIENT_TIMEOUT, указывающие на потерю корректности под нагрузкой. Порог - Неизвестно.

## Неизвестные параметры

- Целевые значения RPS по шагам и итоговая целевая пропускная способность.
- Длительность шага нагрузки (STEP_DURATION) и общая длительность прогонов.
- Допустимые latency percentiles (p50/p95/p99) и error rate для принятия решения.
- Параметры тестового стенда (CPU, память, сеть), среда запуска и изоляция внешнего LLM.
- Конкретные коды и структура «контролируемого ответа» при таймауте внешнего LLM (REL-1 не задаёт формат).
- Хост/порт ENDPOINT и аутентификация/заголовки, если требуются.
- Способ имитации медленного/недоступного LLM (mock, fault injection, отключение сети).
- Источник и формат логов (LOG_SOURCE) и способ привязки request_id.
