Findings (по критичности)
- Критично — отсутствие валидации входа и возможный KeyError
- app/api.py:36-37 — create_review(payload: dict) обращается к payload["diff"] без проверки. При отсутствии ключа будет KeyError → 500 вместо корректного 4xx. Нет проверки, что diff — строка и не пустой. Риск для стабильности API.
- Критично — отсутствие ограничений на размер входа
- app/api.py:36-37; app/review_service.py:19-22 — передается произвольный diff любой длины в LLM. Это может вызвать чрезмерное потребление ресурсов/время ответа, нестабильность и затраты. Нужны лимиты/валидация/тримминг.
- Существенно — синхронная обработка потенциально блокирующей операции
- app/api.py:36-37 — эндпоинт синхронный, review_service.review вызывает LLM синхронно. Если LLM-клиент делает сетевые вызовы, это блокирует воркер и снижает пропускную способность. В FastAPI стоит либо сделать async def и вызывать через threadpool, либо использовать асинхронный клиент.
- Существенно — отсутствие обработки ошибок LLM
- app/review_service.py:21-22 — исключения из self.llm.generate не перехватываются; клиенту вернется 500 без диагностической информации. Стоит маппить на 502/503/504 с понятным сообщением.
- Существенно — отсутствие схем (request/response) для OpenAPI и валидации типов
- app/api.py:36 — payload: dict слишком общий, теряется схема в документации и автоматическая валидация. 
- app/api.py:36-37,39 — нет модели ответа; OpenAPI будет менее точным. Это усложняет интеграцию клиентов.
- Существенно — зависимость от версии Python для подсказок типов
- app/api.py:36; app/review_service.py:19 — используется dict[str, str], что требует Python 3.9+. Если проект на <3.9, это сломает импорт. Уточнить целевую версию.
